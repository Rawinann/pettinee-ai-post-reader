# โมเดลจำแนกความต้องการของโพสต์

ทำงานด้วยโมเดลที่ฝึกจริง: **TF-IDF ตัวอักษร 2–5 ตัว + Logistic Regression** ฝึกด้วย scikit-learn และส่งออก vocabulary, IDF, coefficients และ intercepts เป็น JSON ให้ Node.js ทำนายบนเครื่องได้โดยไม่เรียก Python หรือ API ภายนอกขณะเปิดเว็บ

## สถานะที่ต้องเข้าใจก่อนใช้

รอบแรกใช้ป้ายร่างที่ผู้ช่วย AI จัดจากการอ่านข้อความตัดตอน ไม่ใช่ป้ายที่คนยืนยัน และไม่ใช่ข้อมูลการวินิจฉัย ใช้เพื่อทดลอง pipeline และ UX เท่านั้น ยังอ้างความแม่นยำใช้งานจริงไม่ได้

ไฟล์ต้นทางมี 200 รายการ มีข้อความ 179 รายการ อีก 21 รายการถูกตัดออกจากการฝึก/ทดสอบ ไม่สร้างข้อความหรือคอมเมนต์เติมเอง ข้อความสาธารณะตัดตอนอาจมีคำอธิบายจาก Meta ปะปน เป้าหมายจึงเป็นความต้องการที่เห็นในข้อความส่วนนี้ ไม่ใช่เจตนาที่ทราบแน่ชัดของเจ้าของโพสต์เต็ม

ใช้ **เฉพาะข้อความ** เป็น features ไม่ใช้คำค้น URL หมวด ชื่อผู้เขียน หรือคอมเมนต์ และไม่ใช้คำค้นเป็น ground truth การเลือกประเภทจากหน้าอ่านโพสต์ใช้เพื่อเปิดเครื่องมือเท่านั้น ไม่ถูกนำไปฝึกโดยอัตโนมัติ

## นิยามป้าย

| รหัส | ความหมายและตัวอย่างขอบเขต | จำนวนป้ายร่าง |
| --- | --- | --- |
| `advice` | ขอข้อมูล คำอธิบาย หรือวิธีจัดการ เช่น “เกิดจากอะไร” ไม่ตอบคำถามการรักษาให้ | 80 |
| `compare` | ขอรีวิว ขอแนะนำตัวเลือก หรือเทียบสินค้า งบที่เป็นเงื่อนไขการเลือกยังอยู่กลุ่มนี้ | 19 |
| `cost` | ถามราคา ค่าใช้จ่าย หรือบริการที่เกี่ยวกับการวางแผนค่าใช้จ่าย | 7 |
| `experience` | เล่าประสบการณ์ รีวิวของตน หรือแบ่งปันเนื้อหาความรู้ ไม่ใช่การรับรองว่าเนื้อหานั้นถูกต้อง | 12 |
| `unclear` | เป็นเพียงข้อสังเกต ข้อความตัดขาด หรือยังระบุความต้องการหลักไม่ได้ | 61 |

เลือกความต้องการหลักหนึ่งข้อ ถ้าก้ำกึ่งให้ใช้ unclear และทบทวนกับผู้ตรวจอีกคน ไม่อนุมานความกังวลหรือการขอรักษาจากชื่อโรคเพียงอย่างเดียว เช่น “ไม่มีเงิน ทำอย่างไรดี” อาจขอคำแนะนำ แต่ “ค่ารักษากี่บาท” เป็นคำถามค่าใช้จ่าย

## ผลทดลองรอบแรก

แบ่งด้วย StratifiedGroupKFold เก็บชุดทดสอบคงที่ 37 ข้อความ ฝึก 142 ข้อความ กลุ่มข้อความซ้ำหรือใกล้เคียงมากจาก SequenceMatcher >= 0.86 ไม่ข้ามชุด ฝึก TF-IDF ภายใน train เท่านั้น และทำ cross-validation 3 folds เฉพาะชุดฝึก ไม่มีการปรับ threshold จากคะแนนชุดทดสอบ

| วิธี | Macro-F1 เทียบป้ายร่าง |
| --- | --- |
| Keyword baseline | 0.677 |
| TF-IDF + Logistic Regression ก่อนเกณฑ์ให้คนตรวจ | 0.815 |
| ผลหลังเกณฑ์ให้คนตรวจซึ่งใช้บนเว็บ | 0.616 |

เกณฑ์ต้นแบบคือคะแนนสูงสุดต่ำกว่า 0.55 หรือคลาส unclear ให้ผู้ใช้เลือกเอง คะแนนนี้ยังไม่ calibrate จึงไม่แสดงเป็นเปอร์เซ็นต์ความถูกต้อง เว็บเสนอประเภทได้ **9 จาก 37** ข้อความทดสอบ อีก **28 จาก 37** ขอให้ผู้ใช้ตรวจหรือเลือกเอง เกณฑ์นี้ทำให้มีการงดเสนอค่อนข้างมาก ยังต้องพัฒนาจากข้อมูลที่คนตรวจแล้ว ไม่ซ่อนข้อจำกัดด้วยการรายงานเฉพาะ 0.815

Cross-validation บนชุดฝึกได้ 0.731, 0.642, 0.521 แสดงความแปรผันจากข้อมูลน้อย ชุดทดสอบมี advice 16, compare 4, cost 2, experience 3, unclear 12 ข้อความ การได้ F1 สูงในคลาสที่มีเพียง 2–4 ตัวอย่างยังสรุปผลทั่วไปไม่ได้

รายงาน JSON มี precision/recall/F1 รายประเภท confusion matrix และรายการที่ทำนายผิดอยู่ใน `models/intent-report.json` ทุกตัวเลขเป็น agreement กับป้ายชุดนี้ ไม่ใช่ clinical accuracy

## เปิดใช้งาน

```powershell
node server.mjs
```

เปิด http://127.0.0.1:4173 ถ้าเซิร์ฟเวอร์เดิมยังทำงานอยู่ ให้หยุดแล้วเปิดใหม่เพื่อโหลดเส้นทาง ML

- เปิดโพสต์ แล้วกด **จำแนกความต้องการของโพสต์** ตรวจหรือแก้ประเภทก่อนกดทำต่อ
- หรือไป **เครื่องมือข้อมูล → AI จำแนกโพสต์ / ตรวจป้าย** วางข้อความเพื่อทดลอง
- ผลเสนอเปิดเครื่องมือที่มีอยู่ เช่น เพิ่มข้อมูล ตารางเปรียบเทียบ คำถามเรื่องงบ หรือสมุดบันทึก
- ถ้าข้อความเคยอยู่ใน train จะแจ้งว่าไม่ใช่ผลทดสอบกับข้อความใหม่
- สรุปและคำตอบส่วนอื่นของเว็บยังเป็น Demo แยกจากส่วน ML นี้ ไม่มีการเชื่อม MeongSilJang API

## ตรวจป้ายด้วยคนก่อนพัฒนารอบต่อไป

หน้า ML มีส่วน **ตรวจป้ายกำกับเพื่อพัฒนาโมเดล → เปิดรายการตรวจ** อ่านข้อความ เลือกประเภท และกดยืนยันว่าอ่านแล้วก่อนบันทึก ป้ายร่างจะไม่ถูกเลือกให้ล่วงหน้า และเปิดดูป้ายร่างได้แยกต่างหาก

บันทึกลง `data/intent/annotations.json` บนเครื่อง เก็บ draftLabel เดิม แหล่งที่มาของป้าย และสถานะ reviewed พร้อม revision ป้องกันหน้าต่างอื่นเขียนทับ ไฟล์นี้ไม่มีระบบระบุตัวตนผู้ตรวจ คำว่า reviewed หมายถึงผู้ใช้ในเครื่องยืนยัน ไม่ได้แปลว่าสัตวแพทย์รับรอง หากต้องการ gold dataset สำหรับงานวิจัย ควรมีแนวทางเดียวกัน ให้ผู้ตรวจอย่างน้อยสองคนตรวจบางส่วนโดยไม่เห็นผลโมเดล และตกลงป้ายที่เห็นต่าง

อย่าแก้โมเดลหรือ threshold ตามข้อผิดพลาดใน test ซ้ำ ๆ ให้เลือกค่าบน train/validation และใช้ test สรุปผลหลังตัดสินใจแล้ว การตรวจป้าย test ทำจากข้อความและแนวทางติดป้าย ไม่ใช่เปลี่ยนเฉลยให้ตรงกับผลโมเดล

## เทรนซ้ำ

ทดสอบกับ Python 3.14 แพ็กเกจที่ติดตั้งจริงถูกตรึงไว้ใน `ml/requirements-lock.txt` การเปิดเว็บใช้ Node.js อย่างเดียว ไม่ต้องติดตั้งแพ็กเกจ Python หากใช้โมเดลที่ส่งให้

```powershell
python -m pip install --target ml-deps -r ml/requirements-lock.txt
python ml/train.py
```

คำสั่งปกติใช้ป้ายที่มีอยู่ รวมป้ายร่าง และติดป้ายผลทดลองว่า draft ถ้ายังมี draft แม้เพียงรายการเดียว เมื่อตรวจป้ายครบพอทุกประเภทให้ใช้:

```powershell
python ml/train.py --reviewed-only
```

โหมด reviewed-only ไม่ใช้ draft และจะหยุดถ้ามีตัวอย่างน้อยกว่า 5 ต่อประเภทหรือแบ่ง train/test ไม่ครบประเภท โดยไม่เขียนทับโมเดลเดิม ห้ารายการต่อประเภทเป็นเพียงเกณฑ์ให้ pipeline ทำงาน ไม่ใช่จำนวนที่รับรองคุณภาพ ส่วนแยกข้อมูลถูกบันทึกไว้ หาก corpus เปลี่ยน script จะหยุดให้เก็บรุ่นเก่าและทำชุดแบ่งรุ่นใหม่

`ml/prepare_corpus.mjs` สกัดไฟล์เดิมซ้ำได้และปฏิเสธการเขียนทับ corpus ที่เปลี่ยนไป ส่วน `ml/prepare_labels.mjs` ใช้เริ่มป้ายร่างครั้งแรกเท่านั้น และปฏิเสธการทับ annotations ที่มีอยู่แล้ว รุ่นที่เทรนแล้วเก็บสำเนาโมเดล รายงาน ป้ายและ corpus ใน `models/history/`

## ขั้นต่อไป: ค้นหาโพสต์ความหมายใกล้กัน

เตรียม `data/retrieval/documents.jsonl` จำนวน 179 เอกสารพร้อม ID, URL, sourceNote และ contentHash แล้ว ผ่าน `node ml/prepare_search_corpus.mjs` ยังไม่มี embeddings หรือดัชนี และยังไม่ได้เรียกการค้นหาปัจจุบันว่า semantic search

ขั้นต่อไปคือเลือก embedding model ที่รองรับไทย สร้างเวกเตอร์ในเครื่อง ค้นความใกล้เคียง และทำชุดคำถามทดสอบความเกี่ยวข้องที่คนตรวจ ใช้ Recall@k/MRR และเทียบกับ keyword search โดยวัดคนละงานกับ intent classifier โพสต์ที่คล้ายกันเป็นเพียงตัวอย่างให้อ่าน ไม่ใช่หลักฐานว่าแมวเป็นโรคเดียวกันหรือควรรักษาแบบเดียวกัน
